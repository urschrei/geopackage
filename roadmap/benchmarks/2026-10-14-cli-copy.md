# `gpkg copy` against `ogr2ogr`

On 2026-10-14 `gpkg copy` from 0.10.2 took 1.0 to 1.7 times as long as
`ogr2ogr` to copy the three benchmark datasets. Three changes close the gap:
the output is written with `synchronous = OFF`, the file is not synced at
the end, and each layer is read on a second thread while the first thread
writes. After them, `gpkg copy` is within 5 % of GDAL 3.13.3 on all three
datasets and uses 5 to 6 times less memory.

## Environment

- Fly.io Machine, `performance-8x`: 8 dedicated AMD EPYC vCPUs, 16 GB, region
  `ams`, Ubuntu 24.04 userland. Provisioned by `scripts/bench_fly.sh`.
- `gpkg` release build, bundled SQLite 3.53.2.
- GDAL 3.13.3 from conda-forge, linking SQLite 3.54.0. GDAL 3.8.4 from
  Ubuntu.
- hyperfine 1.18.0: one warm-up, then the stated number of runs, with the
  output deleted and `sync` run before each.
- The `ogr2ogr` arm is
  `ogr2ogr -f GPKG -lco SPATIAL_INDEX=NO -preserve_fid -gt 10000`, which
  matches what `gpkg copy` does with an unindexed source: keep the fids,
  commit every 10,000 rows, build no index.
- The datasets are those of [2026-07-25-real-datasets.md](2026-07-25-real-datasets.md):
  `admin` (356,508 multipolygons, 2.7 GB), `rivers` (8,477,883 linestrings,
  2.0 GB) and `buildings` (11,542,912 polygons, 2.4 GB), all unindexed.

## Starting point

Medians of 5 runs, `gpkg` 0.10.2 against GDAL 3.8.4:

| dataset | `gpkg copy` | `ogr2ogr` |
|---|---|---|
| admin | 20.03 s | 11.85 s |
| rivers | 35.17 s | 28.53 s |
| buildings | 31.17 s | 30.57 s |

## Where the time went

**Syncs.** `strace` counted 232 `fsync` calls for `gpkg copy` on admin and
5,102 on rivers, and none for `ogr2ogr`. GDAL sets `PRAGMA synchronous = OFF`
on a GeoPackage it creates (`ogrgeopackagedatasource.cpp`). With `fsync` made
a no-op by `eatmydata`, `gpkg copy` took 14.1 s on admin and 31.1 s on
rivers. `ogr2ogr` did not change.

**One thread.** `gpkg copy` read and wrote on one thread, so its CPU time
equalled its wall time. GDAL 3.8.4 and 3.13.3 both report
`OGR2OGR: Using WriteArrowBatch()` and `GPKG: Using 4 threads`: they read
Arrow batches and write them through a pool of threads.

**The final sync.** A first version synced the output once, after closing
it. This made admin slower than before (27.1 s): with `synchronous = OFF` the
whole 2.7 GB is still in the page cache at the end, and one sync waits for
all of it at the volume's write speed. `ogr2ogr` and `cp` do not sync at all.
The final sync was removed, and the command documentation says to run `sync`
when the output must be on disk when the command returns.

## Phases, and two ways to overlap them

A scratch program timed each half of the copy alone, and two ways to overlap
them, each with `synchronous = OFF` and no final sync. Medians of 3 runs:

| variant | admin | rivers | buildings |
|---|---|---|---|
| read only | 3.6 s | 10.8 s | 5.4 s |
| write only, rows already in memory | 10.4 s | 21.0 s | 22.5 s |
| reader thread and writer thread | 11.2 s | 25.6 s | 23.2 s |
| `read_arrow` into `write_arrow` | 9.9 s | 22.6 s | 23.9 s |
| `ogr2ogr` 3.8.4 | 11.0 s | 27.1 s | 28.3 s |

The write is the longer half, and the two-thread version comes within 0.7 to
4.6 s of it. The Arrow version is 1 to 3 s faster on admin and rivers, but it
changes some values: a `DATETIME` is re-formatted, an integer in a `REAL`
column becomes a real, and a `BOOLEAN` of 2 becomes 1. It also fails the
whole layer on a cell whose storage class differs from the declared type.
`gpkg copy` uses the two threads, which copy every value unchanged.

## Result

Mean ± σ of 5 runs:

| dataset | `gpkg copy` | `ogr2ogr` 3.13.3 | `ogr2ogr` 3.8.4 |
|---|---|---|---|
| admin | 10.66 ± 0.76 s | 10.94 ± 0.33 s | 10.87 ± 0.14 s |
| rivers | 23.50 ± 1.47 s | 23.22 ± 0.19 s | 26.85 ± 0.40 s |
| buildings | 26.59 ± 0.88 s | 25.31 ± 0.37 s | 29.34 ± 0.19 s |

Peak resident memory, two runs each:

| dataset | `gpkg copy` | `ogr2ogr` 3.13.3 | `ogr2ogr` 3.8.4 |
|---|---|---|---|
| admin | 215 to 229 MiB | 1.29 to 1.30 GiB | 1.29 to 1.30 GiB |
| rivers | 21 MiB | 95 to 96 MiB | 96 to 97 MiB |
| buildings | 15 MiB | 96 MiB | 96 to 97 MiB |

- Against GDAL 3.13.3, `gpkg copy` is 1.03 ± 0.08 times faster on admin,
  1.01 ± 0.06 times slower on rivers, and 1.05 ± 0.04 times slower on
  buildings.
- GDAL 3.13.3 is 16 % faster than 3.8.4 on rivers and buildings, and level
  on admin.
- `gpkg copy` uses about 10 s more user CPU than GDAL 3.13.3 on rivers and
  buildings, and about 2 s less system time on admin.
- All three tools wrote the same row counts. The GDAL files are 32 to 53 KB
  larger.
- `gpkg copy` varies two to eight times more between runs than either GDAL:
  21.7 to 25.2 s on rivers, against 23.1 to 23.6 s for GDAL 3.13.3. An
  earlier run of the same code on another machine of the same type gave
  9.2 s on admin and 24.8 s on buildings. The cause is not known.
- The admin peak comes from the chunks between the threads: the reader sends
  a chunk at 1,000 rows or 8 MiB of geometry, and up to 8 chunks wait in the
  channel.

## Reproducing

```sh
scripts/bench_fly.sh start
scripts/bench_fly.sh copy <ref> 5
scripts/bench_fly.sh stop
```

`copy` installs GDAL from conda-forge onto the volume on first use (set
`FLY_BENCH_GDAL` for another version), builds `gpkg` at `<ref>`, and runs
`scripts/compare_gdal_copy.sh` against that GDAL and Ubuntu's. The log is
written to `/data/logs/copy-<commit>.log` on the volume.
