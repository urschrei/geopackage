# Tile read and write throughput (M4)

Date: 2026-07-27. Machine: Apple M-series laptop, macOS 24.6.0, release build,
bundled SQLite. Fixture: a full web mercator ladder, zoom 0 to 7, 21,845 tiles
of 4 KiB each, 101 MB on disk. Reproduce with
`scripts/compare_gdal_tiles.sh 7 5` and `cargo bench -p geopackage --bench tiles`.

## What was measured

| Operation | Median | Rate |
|---|---|---|
| Streaming scan, in process (`tile_bench scan`) | 200 ms | ~108,000 tiles/sec |
| Random by address, in process (`tile_bench random`) | 148 ms | ~146,000 tiles/sec |
| Streaming scan, external wall minus startup floor | 291 ms | 75,000 tiles/sec |
| Random by address, external wall minus startup floor | 149 ms | 147,000 tiles/sec |
| Batch write (`write_all`, one transaction) | 167 ms | ~131,000 tiles/sec |

The in-process and externally observed figures agree for the random read and
differ by about a third for the scan, which is the process startup and page
cache warming the floor subtraction does not fully remove at this size. Quote
the in-process numbers; the external ones are what the comparison script has to
use, because the GDAL arm has no in-process equivalent.

`cargo bench --bench tiles` over a smaller pyramid (zoom 0 to 4, 341 tiles, hot
cache) gives 193,000 tiles/sec for random `get_tile`, 194,000 for
`get_tile_into`, 682,000 for the streaming scan and 122,000 for `write_all`. The
scan is faster there because the whole file is resident; the zoom 7 figures are
the ones to believe for a file that does not fit in cache.

## Against GDAL

`gdalinfo -checksum` over the same file: 8,145 ms, about 2,700 tiles/sec.

That number is **not** this crate's number for the same job. GDAL returns
pixels, because it decodes each PNG; this crate returns the stored tile bytes
and has no decoder. The difference is what the two implementations do, decided
in the M4 scope (`roadmap/06-m4-tiles.md`: bytes in, bytes out, no image codec
in core), not how quickly they do the same thing. Anyone needing pixels out of a
GeoPackage needs GDAL or an image crate on top of this one.

Read as two operations, both are useful: a tile server handing PNGs to a browser
wants the first number, and a raster pipeline wants the second.

## What is not measured here

Allocation behaviour. These paths are dominated by SQLite, so a wall-clock
figure barely moves when an allocation is removed, exactly as
[#28](https://github.com/urschrei/geopackage/pull/28) argues for the index
build. The allocation targets the tile paths are built to (nothing per tile on
the streaming scan, one buffer per tile for `get_tile`, none in steady state for
`get_tile_into`) need the DHAT harness and a Linux runner; tracked in
[#31](https://github.com/urschrei/geopackage/issues/31).
