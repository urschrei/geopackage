# M2 write/read benchmarks — 2026-07-24

Criterion benchmarks for the M2 write path and read path, plus a GDAL CLI write
baseline. Numbers are medians of the criterion sample; conditions and caveats
are recorded below. No conclusions are drawn beyond the measured figures.

## Hardware / software

| | |
|---|---|
| CPU | Apple M2 Pro (`machdep.cpu.brand_string`) |
| Memory | 16 GiB |
| OS | macOS 15.6.1 (build 24G90) |
| Toolchain | rustc 1.97.1, `--release` (workspace `profile.release`: `lto = "thin"`) |
| SQLite | bundled via `libsqlite3-sys` 0.38.1 (SQLite 3.51.3) |
| Criterion | 0.8.2, `sample_size = 10`, `SamplingMode::Flat` |
| GDAL (baseline) | 3.12.3 "Chicoutimi" (`ogr2ogr`) |

Row count: **1,000,000** rows per case (`GPKG_BENCH_ROWS` default). 10M was not
run for the criterion matrix: the triggered index-build path is ~18 s per 1M
rows, and criterion's 10-sample floor makes each such case ~3 min, so a 10M
matrix would run for hours with no new information — the triggered/bulk/unindexed
ratios are already stable at 1M. A 10M extrapolation from the 1M rates is given
under "Notes".

## Commands

```sh
# ours (this machine, otherwise idle):
cargo bench -p geopackage --bench write
cargo bench -p geopackage --bench read
# smaller/faster reproduction:
GPKG_BENCH_ROWS=100000 cargo bench -p geopackage --bench write

# GDAL CLI baseline:
scripts/gdal_baseline.sh 1000000
```

## Method

- **Write.** Each measured iteration gets a fresh `.gpkg` + empty layer built in
  criterion's untimed setup; the timed region is `write_all_with` over 1,000,000
  pre-generated attribute-free features in one transaction (`batch_size = 0`).
  - `unindexed` — no spatial index.
  - `triggered` — an empty 1.4 spatial index is present; the RTree triggers
    maintain it per row as the inserts land (`never_bulk`).
  - `bulk` — an empty 1.4 spatial index is present; rows are inserted with the
    triggers dropped, then the index is built by the D8 shadow-table copy
    (`always_bulk`). This figure **includes** the gate's whole-database
    `PRAGMA integrity_check`, which is O(database) (see the D8 follow-up in
    `roadmap/04-m2-write-rtree.md`).
- **Read.** One 1M-point indexed file and one 1M-point plain file are built once
  and reused (reads do not mutate). The timed region is the `features()` /
  `features_in()` call, which materialises its result set (see the `layer.rs`
  note on eager materialisation).
- **GDAL baseline.** `ogr2ogr` copies a source GeoPackage (built once from a
  generated CSV, untimed) into a fresh one, with `SPATIAL_INDEX=NO` and `=YES`.
  The timed copy therefore includes GDAL's GPKG **read**, so it is a
  *conservative* (slower) proxy for a pure write; our write figure measures write
  only (data already in memory). GDAL's `SPATIAL_INDEX=YES` uses the same
  scratch-shadow-table technique this crate reimplements (D8), so the indexed
  rows are the intended parity comparison. The asymmetry is the honest caveat.

## Write throughput (1M rows)

Median wall time and throughput (higher is better).

| geometry | index mode | time / 1M | throughput |
|---|---|---|---|
| point | unindexed | 809 ms | 1.235 Melem/s |
| point | triggered | 18.47 s | 54.1 Kelem/s |
| point | bulk | 7.31 s | 136.8 Kelem/s |
| linestring | unindexed | 922 ms | 1.084 Melem/s |
| linestring | triggered | 18.55 s | 53.9 Kelem/s |
| linestring | bulk | 7.48 s | 133.6 Kelem/s |
| polygon | unindexed | 959 ms | 1.043 Melem/s |
| polygon | triggered | 18.35 s | 54.5 Kelem/s |
| polygon | bulk | 7.81 s | 128.0 Kelem/s |

Bulk vs triggered (the D8 result): the bulk shadow-table build is **~2.4–2.5x**
faster than per-row triggered maintenance at 1M rows (point 2.53x, linestring
2.48x, polygon 2.35x), even with the whole-database `integrity_check` gate
included in the bulk figure. Unindexed inserts run at ~1 Melem/s regardless of
geometry; the index build is the dominant cost once a spatial index is present.

## Read throughput (1M point rows)

| query | path | time | throughput |
|---|---|---|---|
| `features()` full scan | plain | 148 ms | 6.76 Melem/s |
| `features_in` full-cover box | RTree | 456 ms | 2.19 Melem/s |
| `features_in` small box (~0.25%) | RTree | 930 µs | (latency; see note) |
| `features_in` small box (~0.25%) | full scan | 71.5 ms | 14.0 Melem/s |

The small-box RTree query (930 µs) is **~77x** faster than the equivalent
full-scan filter (71.5 ms) — the index result is materialised directly, the scan
must test all 1M envelopes. Its criterion `elem/s` figure is elements(=1M) ÷
time, i.e. domain scanned per second, not rows returned, so read the latency.
`features()` (148 ms) is slower than `features_in`'s small-box scan (71.5 ms)
because `features()` materialises all 1M rows into owned `Feature`s, whereas the
box scan tests each envelope first and materialises only the ~2,500 matches (see
the `layer.rs` materialisation note).

## Ours vs GDAL

Reading `ogr2ogr`'s figure as read+write+index and ours as write(+index) only:

- **Unindexed writes are competitive.** Our write-only point load is 0.81 s
  against GDAL's 1.22 s read+write; we do less work and are faster, so the
  honest reading is same order of magnitude / rough parity once GDAL's read is
  accounted for.
- **The indexed/bulk path is not at parity.** GDAL's indexed point copy is
  1.89 s (including the source read); our bulk indexed point write is 7.31 s —
  roughly **3-4x slower**, and the gap holds for lines and polygons. So the D8
  bulk build, while ~2.5x faster than our own triggered path, is well below
  GDAL's indexed loader, which uses the same shadow-table technique in C.
- **Where our bulk time goes (documented, not profiled here):** beyond the
  ~0.8 s raw insert, the bulk figure carries (a) the gate's whole-database
  `PRAGMA integrity_check`, which is O(database), and (b) a per-row `ST_*`
  envelope scan (four registered-function calls × 1M rows) to accumulate
  envelopes. Both are already-open D8 follow-ups in
  `roadmap/04-m2-write-rtree.md` (scope the structural check to
  `rtreecheck(<rtree>)`; build the scratch RTree in a separate connection). This
  benchmark is the evidence those follow-ups were waiting on: the parity target
  ("bulk indexed write ≥ GDAL") is **not yet met** and stays open.

## Notes

- The bundled SQLite is 3.51.3 (not 3.53 as an earlier roadmap note said).
- 10M was not measured directly; extrapolating the stable 1M rates: unindexed
  ~10 s for 10M (~1 Melem/s), triggered ~3 min (~55 Kelem/s), bulk ~75 s
  (~130 Kelem/s). Run `GPKG_BENCH_ROWS=10000000 cargo bench` to confirm.
- The criterion `+30000%`-style regression lines in a fresh run are an artefact
  of comparing against a smaller saved baseline (e.g. a `GPKG_BENCH_ROWS=3000`
  verification run); delete `target/criterion` before a clean measurement run.
- The machine was otherwise idle during measurement; each 1M write case is
  criterion's 10-sample floor, so the spread is ~5-10%.
